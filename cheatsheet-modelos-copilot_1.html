Default · diario

El caballo de batalla. Fuerte en Java/Spring y barato.
  • Implementación de historias
  • Tests y refactors mecánicos
  • Las corridas de /implement de Spec Kit
  • Invocar prompts simples (formateo, traducción de specs)
Tu punto de partida en el 90% de las tareas.

El cerebro pesado. Solo donde la dificultad paga el 3x.
  • Razonamiento arquitectónico (idempotencia, Store & Forward)
  • Revisión de un diff complejo
  • Debugging de concurrencia sutil (ej. @Async via this)
  • Generar constitution / plan / refinar specs con calidad
  • Correr los skills migrados (refinar-spec, analizar-api, etc.)
⚠ 3x premium requests. Con 4 devs, el consumo se multiplica.
Contraste · 2da opinión
GPT-5.2 1x
Cuando Sonnet se atasca. Falla distinto, ve otra cosa.
  • Segunda perspectiva en un problema trabado
  • Contraste de diseño antes de decidir
No es default; es la herramienta de desempate.
Alternativa · opcional
GPT-5.3-Codex 1x
Para edición agéntica pura de código.
  • Cambios de código mecánicos multi-archivo
  • Alternativa a Sonnet si querés probar otro estilo
Útil tenerlo, no imprescindible.
Rubber Duck · personal · fuera del IDE
🦆 Claude Opus 4.7 — Claude.ai externo · personal
El sillón de pensamiento. Para razonar el approach antes de escribir spec o código. NO es canal corporativo — reglas estrictas de saneamiento abajo.
✓ Sí va al rubber duck
  • Preguntas genéricas de Java/Spring
  • Patrones abstractos ("idempotencia entre dos downstreams divergentes")
  • Trade-offs conceptuales
  • Pseudocódigo y diseños sin nombres reales
  • Aprender un framework o decisión técnica
  • Repasar antes de escribir spec en Copilot
✗ Nunca va al rubber duck
  • PAN, CVV, tokens, números de tarjeta — ni de prueba
  • Nombres de sistemas (Monibyte, CaBaaS, TSYS, DAVIPRO) — usá "Downstream A/B"
  • Código con lógica de negocio bancaria — paraseá a ejemplo genérico

  • Diagramas de arquitectura con nombres reales
Test mental: "¿lo pegarías en un thread público de Twitter?" Si no, no va. Treat it like an external consultant under NDA.

03 Reglas de oro

Evitá "Auto" en código crítico

Querés control determinista de qué modelo toca el código. Auto puede caer silenciosamente a un modelo Standard.

1 sesión por sub-fase

Una conversación de Copilot Chat por sub-fase de implementación, en modo Agent. Arrancá limpia para no contaminar el contexto.

Contexto estable en el repo

AGENTS.md, constitution y los docs de negocio van en /docs/ del repo (o el playbook). Copilot los lee del workspace, sin MCP. No uses Spaces — bloqueado en la org.

El 3x importa

Opus se siente mejor, pero cuesta 3x. Usalo donde la dificultad lo justifica, no como driver diario — sobre todo replicado en 4 devs.

04 Monitoreo & límites

Dónde mirar el consumo

Personal — cada dev

  • Web: github.com/settings/copilot → barra de Premium requests
  • IntelliJ: panel del plugin → Account / Usage
  • Reset: el día 1 de cada mes a 00:00 UTC

Equipo / Org — Alvaro o admin

  • Web: github.com/orgs/DaviviendaPanama/settings/billing → Usage
  • Reportes descargables por miembro
  • Pedir al owner visibilidad o reporte semanal

Cadencia recomendada

Primer mes (rollout)

  • Lunes: cada dev revisa su % personal
  • Daily corto: 1 minuto, "¿alguien cerca del cap?"

Régimen estable

  • Día 25: revisión mensual antes del reset
  • Alvaro centraliza un reporte de equipo mensual

Eventos críticos & reservas de cupo

Pases a producción, releases, auditorías, demos: si algo se complica vamos a querer Copilot a mano. Si para esa fecha estamos cerca del cap, mal asunto. Anticipá.

T-7 días — check anticipado

  • Cada dev pulla su % personal
  • Alvaro / tech lead pulla el reporte de org
  • Quien esté >70% baja a Sonnet esa semana
  • Pre-stage los .prompt.md de diagnóstico que vayan a necesitar
  • Pre-mortem con rubber duck (abstracto, sin datos)

T-0 — día del evento

  • AI responder designado: 1-2 devs con cupo disponible quedan en standby
  • Tech lead reserva su seat completo para triage de incidente
  • El resto trabaja con Sonnet o pausa lo no-crítico
  • Post-evento: exportar sesiones relevantes para retro/post-mortem

★ Pair programming como pooling de cupo

Modalidad driver-navigator: solo el driver tiene IDE abierto, su cuenta consume. Dos cerebros, un cupo. Ideal pre-deploy y para el trabajo crítico cuando el cupo del equipo está al filo. Trade-off: productividad por dev-hora baja, pero es el trade-off correcto cuando el cupo es el cuello de botella.

Si llegás al tope · playbook

A

Cambiá el mix. Bajá Opus al mínimo, mové todo lo que puedas a Sonnet 4.6. Sigue funcionando, solo cambia el modelo.

B

Esperá el reset del día 1. Si quedan pocos días, manejable. Mientras tanto, GPT-4.1 standard sigue disponible para tareas livianas.

C

Pedí aumento al banco. Los owners de la org pueden habilitar paid overage o ampliar el budget. Justificá con el reporte de uso del mes.

D

Descartado: caer a Claude.ai personal con datos del banco. Por compliance, no. Solo el rubber duck con saneamiento estricto.

Anti-patterns que queman requests

  • Reintentar prompts grandes idénticos esperando otra cosa. Replanteá, no repitas.
  • Conversaciones eternas de 50 turnos. Sesión nueva limpia consume menos.
  • Copilot Code Review tiene multiplicador 13x desde 1-jun-2026. Usalo selectivamente, no en PRs pequeños.
  • Auto-completes agresivos en archivos enormes. Cerrá el archivo cuando no estés trabajándolo.
05 Revisar este documento

Por qué — los modelos evolucionan

Hoy Opus 4.6 es la mejor opción de razonamiento. En 3-6 meses puede ser otro modelo, o el sistema de billing puede haber cambiado (de hecho, ya cambia el 1 de junio). Este doc debe envejecer con gracia.

Cadencia fija

  • Quarterly review (cada 3 meses)
  • Rota la persona que la hace
  • 1 hora: benchmark de 3 tareas reales (implementación, refinar spec, debugging) en modelos nuevos

Triggers fuera de calendario

  • El banco habilita un modelo nuevo
  • Cambia el billing (junio 2026)
  • GitHub anuncia algo grande en github.blog/changelog
  • Anthropic / OpenAI sacan modelo
06 Gestión de conversaciones

Lo que NO existe (y no busquen)

  • ❌ No hay tags ni keywords nativos en sesiones
  • ❌ No hay carpetas ni grupos
  • ❌ Una sola conversación a la vez en el chat del IDE (feature request abierto)
  • ❌ No hay pin nativo

Lo que SÍ existe y usamos

  • ✅ Persisten entre reinicios (.idea/copilot/chatSessions)
  • ✅ Unified sessions view con filtro por agente / estado y búsqueda por título
  • ✅ Copilot CLI agent en worktree separado = paralelismo real (requiere habilitar "Editor preview features")
  • ✅ Plugin third-party Copilot Chat Exporter para archivar a MD/HTML

Convención de nombres = nuestro sistema de tags

Como el título es el único metadata buscable, el título ES el tag. Renombrá la sesión apenas la abrís.

[TICKET]-[FASE]-[VERBO]-[TOPIC]

Ejemplos

  • CCACCS-254-P3-impl-redis-config
  • CCACCS-254-P4-debug-async-this
  • CCACCS-254-design-store-forward
  • CCACCS-254-refine-spec-monibyte
  • CCACCS-254-review-pr-redis

Vocabulario de verbos

  • impl · implementación de código
  • debug · bug específico
  • design · diseño / arquitectura
  • refine-spec · skill de refinar spec
  • analyze-api · skill de analizar API
  • review · revisar PR / diff
  • investigate · spike / exploración
  • docs · documentación
Pin manual con prefijo
★ o [ACTIVA] al inicio del título — la sesión actual sube al tope. [PAUSE] para sesiones esperando algo externo. Sin prefijo = histórica.

Flujo de archivado & limpieza

1

Sesiones valiosas (la del diseño que se usó, la del post-mortem) → exportar a Markdown → commitear a /docs/copilot-sessions/CCACCS-254/P3/ → borrar del IDE.

2

Viernes EOD: cada dev cierra las sesiones de la semana que no continúan.

3

Fin de sub-fase: export de relevantes al repo, después borrar. Próxima fase arranca limpia.

4

Sin actividad > 2 semanas → se exporta o se borra. No acumular.

Anti-patterns
❌ Misma sesión abierta 3 semanas "porque tiene contexto" — el contexto se infla, gasta más tokens por turno.
❌ Sesiones sin renombrar — en 2 semanas no encontrás nada.
❌ Dos tickets mezclados en una sesión.
